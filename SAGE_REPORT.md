## Code review

The WeatherDashboard module provides basic wrappers around OpenWeatherMap and AirVisual APIs, handling current weather, forecasts, and air‑quality queries. The code is clear and uses environment variables for API keys, with helpful console messages. However, error handling is inconsistent, there is no logging or retry logic, and type safety is lacking, which could cause runtime failures. The design mixes API calls with presentation concerns, limiting maintainability and testability. Minor performance improvements such as request session reuse and response caching are feasible.

**Strengths**
- Clear, well‑documented functions with descriptive docstrings
- Uses dotenv to keep API keys out of source code
- Provides user‑friendly console output for progress and errors
- Logical separation of weather and forecast retrieval

| Severity | Location | Issue | Suggestion |
|---|---|---|---|
| high | `02-weather-dashboard/dashboard.py` | When an API key is missing, the methods return None but callers may assume a dict, leading to AttributeError later in the workflow. | Raise a custom MissingApiKeyError or return a consistent error object; add early validation in the CLI entry point. |
| high | `02-weather-dashboard/dashboard.py` | Error handling relies on generic `except Exception` blocks and `print` statements, which hide stack traces and make debugging difficult. | Replace prints with the `logging` module, use specific exception catches, and re‑raise or propagate errors as needed. |
| medium | `02-weather-dashboard/dashboard.py` | `datetime.now()` is used for timestamps without timezone awareness, while API returns UTC offsets. This can cause misleading times when the user is in a different zone. | Use `datetime.utcnow()` combined with the `timezone` offset or a library like `pytz`/`zoneinfo` to produce timezone‑aware timestamps. |
| medium | `02-weather-dashboard/dashboard.py` | No retry or back‑off strategy for transient network failures; a single timeout failure aborts the request. | Implement retries with `urllib3.util.retry.Retry` via a `requests.Session` or use `tenacity` for exponential back‑off. |
| low | `02-weather-dashboard/dashboard.py` | Hard‑coded `cnt` calculation (`days * 8`) may exceed the API's maximum allowed data points, causing a 400 error for large `days` values. | Validate `days` against API limits (max 5 days for free tier) and cap `cnt` accordingly. |
| low | `02-weather-dashboard/dashboard.py` | Missing type hints and docstring parameter type specifications, reducing IDE assistance and static analysis benefits. | Add type annotations (e.g., `def get_current_weather(self, city: str, units: str = 'metric') -> Optional[Dict[str, Any]]`). |

**Optimization opportunities**
- Create a single `requests.Session` in `WeatherDashboard.__init__` and reuse it for all API calls to benefit from connection pooling
- Cache recent API responses (e.g., using `functools.lru_cache` with a short TTL) to avoid duplicate requests when the same city is queried repeatedly
- Extract API interaction into separate helper classes (e.g., `OpenWeatherClient` and `AirVisualClient`) to improve separation of concerns and simplify unit testing
- Replace repetitive `print` statements with structured logging at appropriate levels (`info`, `warning`, `error`)
- Consider adding a simple CLI argument parser that validates inputs before invoking dashboard methods, improving user experience and reducing runtime errors
